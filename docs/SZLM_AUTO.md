# 自动获取设备标识

应用会把设备标识（数盟 `ShuzlmID`，即数字联盟签发的 DUID）放在每个请求的首字段
`X-App-Device` 里。它缺失或失效时，浏览动态、加载评论会反复要求人机验证。

以前这个标识只能从官方酷安手动复制再粘贴（见 [导入说明](DEVICE_ID_IMPORT.md)）。
现在客户端可以自己注册一个新的标识，不需要安装官方酷安，也不需要粘贴任何内容。
手动导入仍然保留，作为自动获取失败时的兜底。

## 代码位置

| 文件 | 职责 |
|---|---|
| `apps/flutter/lib/utils/szlm_duid_client.dart` | 协议实现：构造 79 字段报文、编码、发送、解密响应 |
| `apps/flutter/lib/logic/szlm_identity_service.dart` | 触发时机、单飞、冷却与次数上限 |
| `apps/flutter/lib/utils/storage_util.dart` | `applySzlmId`：只替换设备编码首字段并落盘 |
| `apps/flutter/lib/pages/settings/device_identity_page.dart` | 设置页：自动获取按钮、手动导入、状态提示 |

整个功能集中在上面四个位置：删掉 `main.dart` 里的 `SzlmIdentityService.instance.ensure()`
与 `request.dart` 里的两处调用即可完全停用，不影响其他逻辑。

## 协议

数字联盟（`cn.shuzilm`）的注册端点在官方客户端里由 `libdu.so` 调用：

```
POST https://auni.telecome.cn/a/mdna/report?v=8.7&t=m&p=<p>&r=<r>&n=0&l=2&h=0
Content-Type: application/x-www-form-urlencoded
User-Agent: Dalvik/2.1.0 (Linux; U; Android 8.1; TK Watch Build/OPM2.171019.012)
Accept-Encoding: identity
```

`p` 是包名派生值（酷安为固定值 `F9BD0FBDACFE80FCF34370FBCFEE1A98`），
`h` 是已有标识的派生值，首次注册为 `0`。

报文是一个 79 字段的 JSON：紧凑格式（无空格）、非 ASCII 原样保留、`/` 写成 `\/`，
然后 zlib（level 6）压缩，再与 48 字节池常量逐字节 XOR。响应走同样两步的逆操作，
`n_a` 就是签发的标识。该标识与官方酷安“复制 OAID”文本里的 `ShuzlmID` 是同一个东西。

每次注册只重抽六个字段：

```
sfOo   7 位大写十六进制
foO    15 字符混淆串
2cO    "秒.纳秒"，纳秒部分必须是新值
w91    32 位大写十六进制
gEd    32 位小写十六进制
6yY    64 位小写十六进制
```

只改前三个（锚点）而不改后三个（设备指纹）时，服务端判定报文不自洽并返回全 0，
所以六个字段必须一起换，识别全 0 响应即为失败。其余 73 个字段保持模板值。

模板为公开研究中的测试设备样本（`TK Watch` / Android 8.1），不含任何用户数据，
仅用于让报文结构与真实客户端一致。

## 触发与限流

| 时机 | 行为 |
|---|---|
| 启动时没有标识 | 后台取一次，成功即写入并用于后续请求 |
| 启动时已有标识 | 完全不联网，沿用已有值（手动导入的值同样保留） |
| 出现人机验证 | 记一笔，在**下一次**请求发出前换号 |
| 冷却 | 自动换号最多 5 分钟一次、每次运行 3 次，超出后交回正常验证流程 |
| 设置页按钮 | 用户明确点击，不受冷却与次数限制 |

换号会同时让 API 会话与验证 Cookie 失效：它们都按设备编码做了身份绑定，所以旧会话
不会被带到新标识上。请求进行中换号时，携带旧设备的响应会被丢弃，不会覆盖新状态。

## 失败与回退

取号失败（离线、接口变更、被限流、响应不可解析）时不弹提示、不覆盖已有标识：

- 启动取号失败：应用照常可用，评论入口显示“设备标识尚未取得”的说明；
- 出现人机验证后换号失败：照常弹出验证界面，用户手动通过即可；
- 设置页点击失败：页面显示简短原因，并提示改用下方手动导入。

内部错误信息不包含报文、响应内容、URL 或异常栈。

## 隐私

- 报文只包含设备指纹字段与包名，不含账号、Cookie、Token 或任何用户内容；
- 报文与响应都不写日志、不进对话框、不进崩溃信息；
- 标识只存本机，用途仅是酷安请求的首字段与网页会话的 `DID`；
- 不读取 IMEI、AndroidID、OAID、UUID 或剪贴板；手动导入仍只在点击时读一次剪贴板。

## 合规与风险

- 该端点属于第三方设备识别服务，能否注册、注册频率和有效期都由服务端决定，
  客户端不做任何绕过：被判不自洽时直接视为失败；
- 接口或协议随时可能变更，届时自动获取会失效，手动导入仍可用；
- 是否接受“客户端自行注册设备标识”由维护者判断；实现保持可整体移除，
  见上文“代码位置”一节的停用方式。

## 实测（2026-10-24）

在 Android 9（x86_64 模拟器，`curl` 直连）上按上文格式发出一次随机三值的注册，
再把它当 `X-App-Device` 首字段打真实接口，三种首字段对比：

| 首字段 | `/v6/feed/replyList` | `/v6/feed/detail` |
|---|---|---|
| 抓包原设备串（40 位 hex，并非 DUID） | `err_request_captcha_v2` 403 | 同左 |
| 本次签发的 DUID | 200，返回 23 条评论 | 200，返回完整正文 |
| 空 | `err_request_captcha_v2` 403 | 同左 |

即：注册链路、TLS 信任、以及“新标识能直接免验证”三件事都成立；而缺失或失效的首字段
正好落到 `messageStatus = err_request_captcha_v2`（`captchaField` 为空，走 `validate`
Cookie 协议），也就是本文“出现人机验证就换号”所依据的信号。

同一次注册的响应还给出 `itime = 604800`（7 天），说明有效窗口由服务端按天决定，
客户端不做推算，只在被挑战时换号。响应当次是**未压缩**的 JSON（与 zlib 压缩的响应并存），
解码器两种都接受。

再用 CI 打出的 debug APK 在同一台设备上验证整条应用内链路：`pm clear` 后冷启动，
应用自己取到 `DUMqtb1J4vCLYfS5OeVLfgeLAZqlvLqPnogbU` 并写入 Hive 的 `szlmId`，
`xAppDevice` 新值首字段即该标识；随后打开一条 69 条回复的动态，评论与楼中楼正常加载，
全程没有人机验证，也不需要手动导入。

## 测试

`apps/flutter/test/network/szlm_duid_client_test.dart` 用固定输入校验编码与解码：

- 固定三值 + 模板指纹时，解出的明文 JSON 与 Python 参考实现
  （`szlm_res` 的 `getduid.py`，MIT）逐字节一致（2337 字符、79 字段）；
- 六个重抽字段各自变化时，明文 JSON 相应改变、其余字段不变；
- 已签发响应可解回标识；全 0 响应、空响应、非 JSON 响应均判为失败；
- 自动抽出的六个字段格式正确，且三个指纹确实随锚点一起变化。

测试不联网：发送函数与随机源都可注入。
